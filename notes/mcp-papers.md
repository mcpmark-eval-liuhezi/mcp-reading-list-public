# MCP Reading List — Papers on the Model Context Protocol

> Search terms used on the local arXiv mirror (and cross-checked against the arXiv abstract pages): `"Model Context Protocol"`, `"Model Context Protocol" AND (security OR attack OR threat OR sandbox OR privilege)`, and `"Model Context Protocol" AND (survey OR "agent architecture" OR "tool use" OR "LLM agents")`. Papers below were shortlisted from those results and their details (title, authors, arXiv ID, submission date, summary) were confirmed on their arXiv abstract pages.

This reading list is focused on **security** first (threat models, attacks, sandboxing, privilege escalation, and mitigations), then the broader picture: surveys, ecosystem measurement, and agent/tool-use architecture work built around MCP.

## Security Papers

### 1. MCP: Landscape, Security Threats, and Future Research Directions
- **Authors:** Xinyi Hou, Yanjie Zhao, Shenao Wang, Haoyu Wang
- **arXiv ID:** [2503.23278](https://arxiv.org/abs/2503.23278) (cs.CR) — submitted 30 Mar 2025 (v3: 7 Oct 2025)
- **Why it matters:** The foundational survey Security researchers needed — it maps the full MCP server lifecycle (creation → deployment → operation → maintenance, 16 activities) and builds a threat taxonomy across four attacker types (malicious developers, external attackers, malicious users, security flaws) with 16 threat scenarios. It pairs the taxonomy with real-world case studies, concrete safeguards per lifecycle phase, and an industry-adoption landscape analysis.
- **Summary:** This paper gives a systematic, security-first treatment of the Model Context Protocol. It defines the complete lifecycle of an MCP server broken into 16 activities, then constructs a threat taxonomy covering four major attacker types and 16 distinct threat scenarios, validated with real-world case studies showing concrete attack surfaces and vulnerability manifestations. It closes with fine-grained, actionable security safeguards per lifecycle phase, an analysis of the current MCP ecosystem (adoption, integration patterns, tools), and future research directions for strengthening MCP's standardization and trust boundaries. It's the best single entry point if you want both the protocol mechanics and the security threat model in one place.

### 2. Systematization of Knowledge: Security and Safety in the Model Context Protocol Ecosystem
- **Authors:** Shiva Gaire, Srijan Gyawali, Saroj Mishra, Suman Niroula, Dilip Thakur, Umesh Yadav
- **arXiv ID:** [2512.08290](https://arxiv.org/abs/2512.08290) (cs.CR) — submitted 9 Dec 2025 (v2: 13 Dec 2025)
- **Why it matters:** A modern SoK (Systematization of Knowledge) that splits *adversarial security threats* (indirect prompt injection, tool poisoning) from *epistemic safety hazards* (alignment failures in distributed tool delegation) — a distinction that matters a lot as MCP servers increasingly act as trust anchors in multi-agent loops.
- **Summary:** This SoK provides a comprehensive taxonomy of risks in the MCP ecosystem, explicitly separating adversarial threats (indirect prompt injection, tool poisoning) from epistemic safety hazards (alignment failures when tool delegation is distributed). It analyzes structural vulnerabilities of MCP's three core primitives — Resources, Prompts, and Tools — and shows how "context" itself can be weaponized to trigger unauthorized operations in multi-agent environments. It surveys state-of-the-art defenses ranging from cryptographic provenance (ETDI) to runtime intent verification, and ends with a roadmap for securing the transition from conversational chatbots to autonomous agentic operating systems. All authors contributed equally.

### 3. Beyond the Protocol: Unveiling Attack Vectors in the Model Context Protocol (MCP) Ecosystem
- **Authors:** Hao Song, Yiming Shen, Wenxuan Luo, Leixin Guo, Ting Chen, Jiashui Wang, Beibei Li, Xiaosong Zhang, Jiachi Chen
- **arXiv ID:** [2506.02040](https://arxiv.org/abs/2506.02040) (cs.CR) — submitted 31 May 2025 (v4: 14 Sep 2025)
- **Why it matters:** The first end-to-end *empirical* evaluation of the MCP attack surface from the client-server integration angle, including a user study showing people can't tell malicious MCP servers from benign ones — useful evidence for any policy conversation about MCPAggregator trust.
- **Summary:** This is the first end-to-end empirical study of attack vectors targeting the MCP ecosystem, identifying four categories: Tool Poisoning Attacks, Puppet Attacks, Rug Pull Attacks, and Exploitation via Malicious External Resources. The authors construct malicious MCP servers and upload them to three widely used MCP aggregation platforms, finding current audit mechanisms insufficient to detect or prevent these threats. A user study with 20 participants shows users struggle to identify malicious servers and often install them unknowingly, and the attacks can trigger harmful local actions (reading private files, controlling devices to transfer assets). The paper closes with four key ecosystem challenges and an urgent call for robust defenses against malicious MCP servers.

### 4. MCPSecBench: A Systematic Security Benchmark and Playground for Testing Model Context Protocols
- **Authors:** Yixuan Yang, Cuifeng Gao, Daoyuan Wu, Yufan Chen, Yingjiu Li, Shuai Wang
- **arXiv ID:** [2508.13220](https://arxiv.org/abs/2508.13220) (cs.CR) — submitted 17 Aug 2025 (v3: 12 Feb 2026)
- **Why it matters:** The first formal spec for what a "secure MCP" even means, plus a working benchmark (with open-source code) that proves current protections are largely ineffective (<30% success-rate of mitigations) across Claude, OpenAI, and Cursor.
- **Summary:** This paper formalizes a secure MCP and its required specifications, then builds a comprehensive security taxonomy that extends existing models with protocol-level and host-side threats, identifying 17 distinct attack types across four attack surfaces. MCPSecBench is a modular, extensible benchmark and playground integrating prompt datasets, MCP servers, clients, attack scripts, a GUI test harness, and protection mechanisms across three major MCP platforms. Their evaluation shows every attack surface yields successful compromises on Claude, OpenAI, and Cursor, with current protections achieving less than 30% average success rate — a sobering empirical anchor for any MCP security roadmap.

## Broader Picture: Surveys, Measurement, and Architectures

### 5. A survey of agent interoperability protocols: Model Context Protocol (MCP), Agent Communication Protocol (ACP), Agent-to-Agent Protocol (A2A), and Agent Network Protocol (ANP)
- **Authors:** Abul Ehtesham, Aditi Singh, Gaurav Kumar Gupta, Saket Kumar
- **arXiv ID:** [2505.02279](https://arxiv.org/abs/2505.02279) (cs.AI) — submitted 4 May 2025 (v2: 23 May 2025)
- **Why it matters:** The right "where does MCP fit" paper — it positions MCP (JSON-RPC client-server tool invocation) against ACP, A2A, and ANP, and proposes a phased adoption roadmap (MCP for tools → ACP for messaging → A2A for collaboration → ANP for decentralized marketplaces).
- **Summary:** This survey examines four emerging agent interoperability protocols: MCP, ACP, A2A, and ANP, each addressing a different slice of the interoperability problem. MCP provides a JSON-RPC client-server interface for secure tool invocation and typed data exchange; ACP defines a general-purpose RESTful HTTP protocol with MIME-typed multipart messages, session management, and DID-based decentralized identifiers; A2A enables peer-to-peer task delegation via capability-based Agent Cards; and ANP supports open network agent discovery using W3C DIDs and JSON-LD graphs. The authors compare them across interaction modes, discovery mechanisms, communication patterns, and security models, and propose a phased adoption roadmap: start with MCP for tool access, layer ACP for structured messaging, Adopt A2A for collaborative enterprise workflows, and extend to ANP for decentralized agent marketplaces.

### 6. A Measurement Study of Model Context Protocol Ecosystem
- **Authors:** Hechuan Guo, Yongle Hao, Yue Zhang, Minghui Xu, Peizhuo Lv, Jiezhi Chen, Xiuzhen Cheng
- **arXiv ID:** [2509.25292](https://arxiv.org/abs/2509.25292) (cs.CY) — submitted 29 Sep 2025 (v3: 15 Nov 2025)
- **Why it matters:** Evidence-based reality check on the MCP ecosystem — over half of listed projects areInvalid or low-value, servers show dependency monocultures and uneven maintenance, and client protocol patterns are still fragmenting. Essential before you treat MCP aggregate stats as trustworthy.
- **Summary:** This is the first large-scale empirical study of the MCP ecosystem, built on MCPCrawler, a systematic measurement framework that collected and normalized data from six major markets over a 14-day campaign, aggregating 17,630 raw entries and analyzing 8,401 valid projects (8,060 servers, 341 clients). The results reveal that more than half of listed projects are invalid or low-value, servers face structural risks including dependency monocultures and uneven maintenance, and clients are in a transitional phase with inconsistent protocol and connection patterns. It's the key evidence-based view of the ecosystem's risks and trajectory that should ground any production adoption decision.

### 7. Bridging Protocol and Production: Design Patterns for Deploying AI Agents with Model Context Protocol
- **Authors:** Vasundra Srinivasan
- **arXiv ID:** [2603.13417](https://arxiv.org/abs/2603.13417) (cs.SE) — submitted 12 Mar 2026
- **Why it matters:** The "MCP works but production doesn't" paper — it identifies three primitives the spec doesn't cover (identity propagation, adaptive tool budgeting, structured error semantics) and proposes CABP, ATBA, and SERF, plus a production readiness checklist.
- **Summary:** This paper argues that while MCP standardizes tool discovery and invocation (10,000+ active servers, 97M monthly SDK downloads), it doesn't yet standardize how agents safely operate those tools at production scale. Through field lessons from an enterprise deployment with a major cloud provider's MCP servers, the author identifies three missing protocol-level primitives: identity propagation, adaptive tool budgeting, and structured error semantics, and proposes three mechanisms to fill them — the Context-Aware Broker Protocol (CABP) with identity-scoped request routing, Adaptive Timeout Budget Allocation (ATBA) framing sequential tool invocation as budget allocation over heterogeneous latencies, and the Structured Error Recovery Framework (SERF) for machine-readable failure semantics. It organizes production failure modes into five dimensions (server contracts, user context, timeouts, errors, observability), includes concrete failure vignettes, and ships a production readiness checklist — valuable for engineers planning real deployments.

## Gaps & Next Steps

Reading this list in order gives you a coherent arc: start with **paper 1** (the threat taxonomy + lifecycle) and **paper 2** (the modern SoK distinguishing adversarial vs. epistemic risk), then move to the empirical attack inventories in **paper 3** (Tool Poisoning, Puppet, Rug Pull) and the benchmark evidence in **paper 4** (MCPSecBench's <30% mitigation success rate). Use **paper 5** to understand MCP's place among ACP/A2A/ANP before committing to a multi-protocol design, and **paper 6** (the measurement study) as a reality check on ecosystem health before trusting any MCP adoption numbers. **Paper 7** is your deployment playbook: it names the three gaps the spec leaves (identity, budgeting, error semantics) and offers concrete patterns + a readiness checklist. Suggested next steps for this project: (a) implement MCPSecBench-style test cases against a small set of real MCP servers you control, (b) read MCPThreatHive (2604.13849) and MCP-38 (2603.18063) for more recent threat-intelligence tooling and a protocol-specific taxonomy, (c) track SMb (2510.15994) and MCPXKit (2508.12538) for complementary benchmarking and analysis tooling, and (d) revisit SMCP (2602.01129) and MCP-Guard (2508.10991) for defense-in-depth and secure-protocol design patterns. Open questions worth chasing: how do sandbox/isolation boundaries interact with MCP's resource and prompt primitives, how do we verify "tool metadata integrity" at scale, and how do we reason about privilege escalation across a Composition of MCP hosts and clients?
